Proposed point values

Scaled to how concentrated each slot's history actually is — not guessed. Lower points where one song (or a small handful) dominates; higher points where the field is wide open. Current flat value is 2 across every slot.

Method for the numbers above: point value = 1 + 5 × (this slot's normalized entropy − the lowest of the 8 slots) / (the highest − the lowest), rounded to the nearest integer. That min–max rescale is a deliberate choice, not a measured fact — see below for why, and for the raw entropy numbers behind it.

Methodology

How this was measured

Why normalized entropy, and why min–max rescale it

Shannon entropy answers "if I had to describe which song fills this slot, how many bits of surprise does the answer carry, on average, across history." A slot where one song wins 60% of the time has low entropy (very predictable); a slot where 80 different songs each show up once has high entropy. Raw entropy in bits isn't comparable across slots that don't have the same number of possible answers, though — a slot with 230 possible covers and one with 72 possible set-2-openers can't be judged on the same bit scale. Dividing by log₂(distinct songs) rescales entropy to 0–1 (normalized entropy, "how close to uniformly random is this slot, given how many answers it could have"), which is comparable across slots, and is what's used everywhere below.

Normalized entropy across these 8 slots turned out to sit in a fairly narrow band (roughly 0.88–0.99) — jam-band setlists are just genuinely varied everywhere, there's no slot that's a near-lock. Mapping that narrow band directly onto a point range would barely differentiate anything after rounding to whole points. So the proposal instead rescales relative to the other slots being priced — the least predictable of these 8 slots gets the top of the range, the most predictable gets the bottom, and the rest interpolate. That's a real methodology choice (and the 1–6 range is a judgment call, easy to change) laid over data-driven ordering and spacing between slots — both parts are shown separately throughout so you can tell which is which.

One correction applied throughout: the plain "count and divide" (plug-in) entropy estimator is a known-biased estimator — it understates true entropy for a finite sample, and the understatement gets worse exactly where a slot has lots of distinct songs relative to how many shows were observed. Every entropy number below is Miller–Madow corrected (a standard, simple correction: + (distinct songs − 1) / (2 × sample size × ln 2) bits) — and the size of that correction is shown per slot, so a big correction reads as a sample-size warning rather than a hidden adjustment.

Discussion

Has the band's behavior actually drifted?

Short answer: the data can't really tell you that at the slot level, and here's why — but a couple of things are worth a gut-check anyway.

Why the "recent" entropy numbers are not a second opinion worth trusting on their own: a year of touring gives each slot roughly 33–97 observations, spread across 20–70+ distinct songs. When most of those songs only show up once or twice in that short a window, normalized entropy mechanically climbs toward its 1.0 ceiling — not because the band got less predictable, but because there simply hasn't been enough time for repeats to show up yet. Several slots hit exactly 1.000 in the recent window; that's the ceiling talking, not a real finding. The point-value proposal above is deliberately based on all-time data for this reason — it's the only window with enough repeats per slot to say something real about concentration.

What is worth a gut-check, because it doesn't depend on trusting a small-sample entropy number: which song is currently the single most-repeated answer in the last year, and whether that matches what your crew would've guessed. Also worth a look — debuts have gotten rarer: That's a real behavioral signal (it's a plain rate, not an entropy estimate), and it's directly relevant to whether the Any Debut wildcard should be repriced (see below).

Caveats & data notes

  • Source & window: The Carton's public API (thecarton.net/api/v2), every show from 2010-01-01 through today at fetch time, pulled fresh for this analysis — not the app's live database.
  • Doubleheaders: 28 dates in the dataset carry two distinct show_ids (a matinee/evening pair, most often). The Carton's setlist endpoint is keyed by date, so both shows arrive in one response — split back into two shows by show_id before anything else runs, or those would've been merged into one artificially-long setlist.
  • Slot definitions reused verbatim from the app: this analysis imports deriveSlotFacts/norm directly from supabase/functions/carton-sync/scoring.js — the actual production scoring code — rather than re-deriving "opener"/"closer"/etc from scratch, so a slot means exactly what it means when a real pick gets scored. One fix on top of that import: scoring.js's own slotImpossible.set1_closer only fires when a show has literally no first set (never, in practice) — it doesn't know about one-set shows, because that exclusion normally happens one layer up, in the admin config, which never offers a Set 1 Closer slot on a one-set show. Without adding that exclusion here too, Set 1 Closer's sample would have silently included two-thirds of the dataset's one-set shows, double-counting the same song under both "Set 1 Closer" and "Set 2 Closer."
  • Encore and Cover Pick are multi-answer slots: a pick hits if it matches any qualifying song, and most shows have more than one (encore: ~1.5 songs/show on average when there is one; cover pick: ~2.3 covers/show on average when there is one). Their concentration numbers count every qualifying song per show as one occurrence, which is the most defensible reading but means their "sample size" and "total occurrences" aren't quite the same number the way they are for the single-song slots — both are reported separately per slot.
  • Song naming is matched case/diacritic/punctuation-insensitively (the same norm() the app's own scoring uses), so "Golden Gate Dancer" and a stray "golden gate dancer" typo in one setlist entry count as the same song. Display names use whichever casing appeared first.
